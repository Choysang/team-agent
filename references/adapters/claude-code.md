# Claude Code 适配
<!-- adapter: host=claude-code; verified=2026-10-27; host_version=2.1.308; evidence=tested -->
[返回能力与宿主分流](../harness-matrix.md) · [返回主流程](../../SKILL.md)

适用于Claude Code CLI、IDE扩展、桌面应用，以及Claude应用中的Claude Code会话。识别依据：派发工具 `Agent`（旧名 `Task`）的参数含 `subagent_type`、`model`、`effort`。核对日期：2026-10-27（官方文档 + 本机实测）。

宿主版本以实际执行本会话的进程为准：桌面应用内嵌自己的Claude Code（Windows上在 `%LOCALAPPDATA%\Claude-Data\...\claude-code\<版本>\claude.exe`，会话内 `/status` 的Claude Code行），可能与终端 `claude --version` 不同；mod门槛按前者判断。

## 宿主事实

| 项目 | 行为 |
|---|---|
| 模型优先级 | 本次调用 `model` > 代理文件 `model` > `CLAUDE_CODE_SUBAGENT_MODEL` > 主会话模型。`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` 时环境变量压过一切 |
| 强度优先级 | `CLAUDE_CODE_EFFORT_LEVEL` > 本次调用 `effort` > 代理文件 `effort` > 会话档位 |
| 可派发值 | 调用参数 `model` 只接受别名（以本次工具枚举为准，常见 sonnet/opus/haiku/fable）；代理文件还接受完整ID与inherit。`effort`：low/medium/high/xhigh/max，不支持时降到不高于它的最高档 |
| 档位表 | Anthropic API上 Opus 5.5、Sonnet 5.5、Haiku 5.5、Fable 5.1 均支持五档；5.5系列默认medium，Fable默认high。其他服务商（Bedrock、Vertex、Foundry）别名解析不同，档位以现场为准 |
| 内置角色 | Explore、Plan、general-purpose、claude等带系统提示词；同名用户文件会整体替换它们 |
| 扩展思考 / Fast | 跟随主会话，无按子代理设置 |
| fork | 继承主模型且不接受effort |
| Mod | 插件中的 `tool.call`、`agent.spawn` 钩子在进程内改写派发；2.1.287+（桌面2.1.286+）可用，组织策略可禁止 |

## 职能到角色类型

每个职能独占一种类型，mod才能按类型区分职能：

| 职能 | subagent_type | 说明 |
|---|---|---|
| Explorer | `Explore` | 内置，只读 |
| ExpertAdvisor | `Plan` | 内置，只读 |
| Executor | `general-purpose`（含 `claude`） | 内置，主代理默认的委派类型 |
| Reviewer / Researcher | `team-reviewer` / `team-researcher` | 生成文件，`disallowedTools: Write, Edit, NotebookEdit`，只读由宿主权限真正保证 |
| Designer / GeneralWorker | `team-designer` / `team-generalworker` | 生成文件 |
| 已有专业代理 | 原名（如python-reviewer） | 按 [role-families.json](../role-families.json) 或名称归入职能，保留原指令 |

## 主方案

一份profile生成三样东西，一起构成唯一的生效方案：

1. **mod `team-agent-router`**（技能根目录的 `.claude-plugin/` 与 `hooks/register.ts`）：在Claude Code进程内运行，不需要Python。Agent工具调用缺 `model` 或 `effort` 时按角色类型补上；主代理显式传的值（用户当次指定、升级阶梯）保留不动。`agent.spawn` 为不经过工具的派发兜底模型，并把引擎实际解析出的模型写入 `~/.team-agent/claude-code/dispatch-log.jsonl`。`/team-agent` 显示路由表与最近派发。任何错误都放行原调用，不会阻断派发。
2. **team-*角色文件**：给Reviewer、Researcher、Designer、GeneralWorker各自独立的类型；frontmatter里带同样的model/effort。四个文件总是一起生成：inherit的职能也有文件（不带model/effort），用来固定“职能→类型”的对应，之后改配置时类型名不变。
3. **CLAUDE.md受管块**：告诉主代理每个职能用哪种类型、升级阶梯怎么走。

降级方案：组织策略（`allowManagedModsOnly`）或 `disableAllHooks` 禁止插件时，只剩第2、3项。此时内置角色（Explore、Plan、general-purpose）依靠主代理按CLAUDE.md显式传参，稳定性低于主方案，汇报中注明。

不使用的做法：settings里的PreToolUse hook（社区报告部分版本对Agent工具忽略 `updatedInput`，见issue #39814、#44412）；覆盖内置角色文件；设置 `CLAUDE_CODE_EFFORT_LEVEL`（会压平所有职能）。可选的 `bind` 只在用户要求时给已有专业代理写入托管的model/effort。

## 执行步骤

状态目录：`~/.team-agent/claude-code/`。claude-home：`$CLAUDE_CONFIG_DIR` 或 `~/.claude`。

### 1. 安装mod（征得用户同意后）

mod是以用户权限运行的代码，先告诉用户它做什么（只改子代理调用的model/effort，写一份派发日志），得到同意再装。三选一：

1. 技能本身放在 `~/.claude/skills/team-agent/`（或项目的 `.claude/skills/team-agent/`）：Claude Code会把技能目录里的插件作为 `team-agent-router@skills-dir` 自动加载，无需其他操作。该目录是指向别处（如 `~/.agents/skills/team-agent`）的链接时同样加载（`claude plugin list --json` 可见）。
2. 技能在别处（如 `~/.agents/skills/team-agent`）：在 `~/.claude/settings.json` 的 `env` 中把技能目录加入 `CLAUDE_CODE_PLUGIN_DIRS`（多个路径用系统路径分隔符，Windows为 `;`），保留已有值。
3. 仅本次会话：`claude --plugin-dir <技能目录>`。

下次新会话生效。确认加载：`/plugin` 的提示行出现 `team-agent-router`，或运行 `/team-agent`。被组织策略或 `disableAllHooks` 阻止时，按上面的降级方案继续。

### 2. 写入配置（有Python 3.11+时）

在技能目录用你的Shell执行。`--dispatch-models` 与 `--dispatch-efforts` 填你自己Agent工具参数里的枚举，即当前真正可派发的值：

```text
python scripts/claude_code_adapter.py onboarding --dispatch-models <model枚举> --dispatch-efforts <effort枚举>
python scripts/claude_code_adapter.py sync --profile <profile.json>
python scripts/claude_code_adapter.py verify
```

`sync` 写入CLAUDE.md受管块、四个team-*文件和mod读取的 `routing.json`。`verify` 核对文件，并报告mod会不会被加载（`mod.will_load` 与加载方式）。

其他命令：`ladder --role <职能> [--from <模型>/<强度>]`（升级阶梯：同模型medium→max，再换更强模型从medium起）、`resolve`（含首选模型的冷却与恢复状态）、`classify --text`（把错误原文分成额度/限流/过载/网络等）、`failover`（切备选并记录冷却）、`recover --role <职能|all>`（冷却结束后回到首选）、`stats --days 7`（按角色类型统计实际派发的模型与强度，并标出与路由表不符的派发）、`preference`、`catalog-ack`、`bind`、`probe`。

### 2'. 没有Python时（手工写同样的内容）

1. `~/.claude/agents/team-<职能>.md`（四个）：
   ```markdown
   ---
   name: team-reviewer
   description: Independent code reviewer. Use proactively after code changes to find concrete defects, regressions and risks.
   disallowedTools: Write, Edit, NotebookEdit
   model: opus        # inherit时省略本行
   effort: medium     # inherit时省略本行
   ---

   Review the stated diff or files. Report only actionable findings, most severe first, with file:line, failure scenario and fix. Do not modify files.

   <!-- generated by team-agent; edit the profile, not this file -->
   ```
   已存在同名但没有该生成标记的文件时停止，请用户改名。
2. `~/.claude/CLAUDE.md` 追加或替换 `<!-- team-agent:claude-code routing:start -->` 与 `:end -->` 之间的块：一张“职能 | subagent_type | model | effort | 剩余备选”表，加上本卡“职能到角色类型”的规则与“fork不承担职能”。
3. `~/.team-agent/claude-code/routing.json`：`{"agents": {"<小写类型名>": {"role": "<职能>", "model": "<别名或inherit>", "effort": "<档位或inherit>"}}}`，内置类型（explore、plan、general-purpose、claude）、team-*和已有专业代理各一项。mod读取它，不需要Python。

### 云端或临时环境

Claude应用中的云端会话每次从新容器启动，`~/.claude` 不会保留。需要长期生效时，把技能放进项目仓库的 `.claude/skills/team-agent/`（mod随技能自动加载），并把 `agents/`、`CLAUDE.md` 写到项目的 `.claude/` 下一起提交；mod读取的路由表用 `TEAM_AGENT_ROUTING` 指向仓库内的文件。不能改仓库时，把路由表文字交给用户放进账户的个人偏好（降级方案）。

## 共存提醒

Cursor与VS Code也会读取 `~/.claude/agents/`。存在 `~/.cursor` 时，按 [Cursor适配](cursor.md) 在 `~/.cursor/agents/` 放同名team-*文件遮蔽，避免把 `opus` 这类别名当作Cursor模型ID。

## 覆盖检查（onboarding、resolve、verify都会做）

- blocking：`CLAUDE_CODE_EFFORT_LEVEL`、`CLAUDE_CODE_SUBAGENT_MODEL_FORCE`（进程环境或settings的env）。
- 警告：settings的 `availableModels` 不含所选模型（宿主会替换）；存在 `~/.cursor`。
- 提示：`CLAUDE_CODE_SUBAGENT_MODEL` 只影响仍为inherit的职能；用户目录下存在同名Explore/Plan/general-purpose文件会替换内置提示词；托管策略、项目设置与mod无法从这里读取，只能靠实测发现。

## 新模型检测

onboarding记录当前Agent工具的model/effort枚举，并从最近的子代理元数据读取别名的实际解析（例如haiku→claude-haiku-5-5）。别名解析到新ID、枚举增减都会生成待处理指纹；新模型档位未知时不补造。期间resolve仍按用户原选择派发并警告，等用户在更新卡中处理后再 `catalog-ack`。

## 运行验证

为每个已配置职能在新会话中派一次最小任务（“只回复pong，不用工具”），记下返回的agentId。证据在 `<claude-home>/projects/*/*/subagents/agent-<id>.meta.json`（请求的agentType/model/effort）和同名 `.jsonl`（每轮 `message.model`、`effort` 与输出）。你可以直接用读文件工具核对，或用 `probe --prepare/--check` 自动核对。

装了mod时，`dispatch-log.jsonl` 每行记录类型、职能、请求的模型、引擎解析出的模型和路由表中的强度（`route_effort`，不是实际强度），可先用它快速核对；最终结论仍以transcript为准。定期用 `stats` 找出偏离路由表的派发。

判定：类型一致、请求参数一致、每轮实际模型属于该别名族、实际effort完全相同（被降档也算不一致）、有输出、晚于本次测试开始、各职能用不同agentId、期间配置未改。inherit/inherit职能记为not_configured，不计入结果。检验mod是否生效：派发时故意不传model/effort，再看meta中的请求值和transcript中的实际模型与强度。

2026-10-27实测（Claude Code 2.1.311）：
- 显式传参：Explore + haiku/max → claude-haiku-5-5 / max；general-purpose + sonnet/high → claude-sonnet-5-5 / high。
- mod补参：派发Explore时不传model/effort，mod补成haiku/max，meta与每轮transcript均为claude-haiku-5-5 / max，dispatch-log记录了解析结果。
- 升级阶梯：Explore配置haiku/max，按 `ladder` 的下一级显式派发sonnet/medium → 实际claude-sonnet-5-5 / medium，mod未覆盖。
- mod保留显式值：general-purpose显式传haiku、不传effort → 模型保留haiku，effort补为high。`stats` 把这类显式改动正确标为偏差。

2026-10-27实测（Windows桌面应用，内嵌Claude Code 2.1.308，技能目录为链接）：
- sync在会话中途写入后，mod约5秒内读到新路由表，team-*类型在同一会话内热加载，无需新会话。
- 五个职能各派一次且均不传model/effort，mod全部补参：Explore→claude-haiku-5-5/max、general-purpose→claude-sonnet-5-5/high、Plan→claude-opus-5-5/max、team-reviewer→claude-opus-5-5/medium、team-researcher→claude-sonnet-5-5/medium；meta请求值、每轮transcript实际值与dispatch-log一致，均有pong输出。
- 子代理历史里若有经第三方服务商的旧记录（如sonnet→mimo-v2.6-flash），`observed_resolutions` 会取到它并把该别名的档位判为未知、sync拒绝；先显式派一次该别名的最小调用刷新解析，再 `catalog-ack`。
