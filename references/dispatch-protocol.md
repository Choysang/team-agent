# 子代理派发、协作与升级

[返回主流程](../SKILL.md) · [能力与宿主分流](harness-matrix.md)

## 谁决定派发

是否派发子代理、派几个、什么时候派，由当前Agent自己判断。Codex、Claude Code这类成熟宿主的派发已经比较科学，本技能不干预，也不鼓励多派。它默认只做一件事：子代理被派出时，按用户的配置使用对应的模型与强度（由各宿主的主方案自动完成）。

## 协作模式（按需启用）

下面的流程只在两种情况下启用：用户明确要求按team-agent的方式协作（例如“用team-agent带队完成”），或者你判断当前任务确实需要多个子代理分工（例如多个独立模块要并行改动）。启用时说一句“已启用team-agent协作模式”；任务完成后自动退出，不延续到之后的对话。

方法综合了三处：oil-oil/codex（调用方定目标与验收、受托方执行、调用方亲自复核）、obra/superpowers（每个任务一个新子代理、按状态处理、审查后才算完成）、Anthropic advisor思路（按用户规则落成固定的升级阶梯）。

### 交代任务

1. 先判职能，再按宿主的主方案解析实际角色类型。保留宿主已有的专业角色。
2. 一次只交一个边界清楚的任务。提示词简短（通常几百字），包含：
   - 目标：要改什么或查清什么，哪些不能动。
   - 完成标准：预期行为与必须覆盖的边界情况。
   - 验证：仓库里真实的测试、lint或构建命令（先从配置中确认，不猜）。
   - 安全边界：不提交git、不顺手重构无关代码；子代理不再派生子代理。
   - 最终报告：改了什么和为什么、动了哪些文件、验证结果、未完成的事项，以及状态（见下表）。
3. 只指出1–4个关键入口文件，让子代理自己探索；不要把大段文件内容或会话历史贴进去。查不到的仓库事实先查，确认不了就说明，不让子代理去猜。
4. 相互独立的任务（不同子系统、不写同一批文件）在同一轮一起派发才能并行；可能相关、要写同一批文件、还在摸清问题时不并行。Executor的写入范围要明确，并告知它其他代理也在工作、不得回退他人修改。

| 状态 | 含义 | 主代理的处理 |
|---|---|---|
| DONE | 完成 | 复核后才采用 |
| DONE_WITH_CONCERNS | 完成但有疑虑 | 先处理正确性或范围上的疑虑 |
| NEEDS_CONTEXT | 缺信息 | 补上信息后继续；这不是能力问题，不升级 |
| BLOCKED | 做不下去 | 判断原因：缺上下文→补；任务太大→拆分；计划有误→修正；能力不足→升级。不原样重试 |

### 复核（调用方负责最终验收）

子代理说“测试通过”不能代替你的验收。先读它的报告，再看实际改动和验证结果：

- 亲自重跑真实的验证命令。
- 检查测试有没有被删除、跳过或放宽；改动有没有超出范围。
- 留意写死的成功结果、被吞掉的异常、未经确认的API、死代码、没有调用方的抽象。
- 并行任务回来后检查有没有改到同一处，再整体验证一次。审查发现的小问题记下延后处理，不进入修复循环。

### 返工

同一级别的返工优先继续同一个子代理会话（Claude Code用SendMessage发给原agentId；Codex继续原线程），只发新的发现和修正，不重述整个任务。需要换模型或强度时（升级阶梯）才新建调用。

## 升级阶梯（结果不合格且原因是能力不足）

每一级都新建调用，显式传入该级的模型与强度：

1. **同一模型，逐级调高强度**：medium → high → xhigh → max（低于medium的档位不用；当前已高于medium时从下一档开始）。
2. **换更强的模型，再从medium开始**：例如Claude Code的 haiku → sonnet → opus → fable，每个模型都是 medium → high → xhigh → max。
3. **阶梯走完**：主代理亲自完成，或向用户说明卡点和已尝试的级别。

- 模型由强到弱的顺序以当前宿主实际可派发的模型为准：由你现场识别，不写死。Claude Code可用 `claude_code_adapter.py ladder --role <职能> [--from <模型>/<强度>]` 直接得到阶梯。
- 同一个问题在同一级重试最多一次，并且要补充更清楚的指令；没有新信息就直接上一级。
- 往上升之前先收窄任务范围；描述写得更长本身不是升级的理由。
- 升级只作用于这一次任务，不改用户保存的配置。
- 宿主不支持单次调用改模型时（见各宿主主方案），阶梯退化为：改派配置了更强模型的职能代理（通常是ExpertAdvisor）→ 主代理亲自完成。

## 失败分类与备选（调用本身失败）

先分类再决定动作（Claude Code：`claude_code_adapter.py classify --text "<错误原文>"`）：

| 类别 | 典型信号 | 动作 | 首选冷却 |
|---|---|---|---|
| quota_exceeded | quota、usage limit、credit balance | 切到下一个备选 | 60分钟 |
| rate_limit | 429、too many requests | 切到下一个备选 | 2分钟 |
| overloaded | 529、503、overloaded | 切到下一个备选 | 5分钟 |
| model_not_found | model not found、invalid model | 切到下一个备选，提示用户更新配置 | 24小时 |
| server_error | 500、502、504 | 同一模型重试一次，重复才切 | — |
| network | 连接重置、超时 | 网络恢复后重试 | — |
| auth | 401、403、未登录 | 报告，不切模型 | — |
| workspace_quota_exceeded | 组织或工作区总额度 | 报告；换模型没有用 | — |
| unknown | 无法归类 | 读原文，原因不明时不切 | — |

- 只用用户选定的有序链，每个备选带各自的强度；同一次失败只切一次，不回绕；链用尽报告阻塞。
- 切换时记录首选模型的冷却截止时间，冷却结束后回到首选（Claude Code：`recover --role <职能|all>`）。
- 已运行的调用不热切，交接必要状态后新建调用，避免重复写入。
- 是否独立计费默认未知。每个模型有独立的提示缓存，换模型会重新写缓存；只记录真实观测的用量，不模拟费用。
